# Bài thực hành - Day 22: Volumes

## Prerequisites

- K3s hoặc Kubernetes cluster đang chạy.
- `kubectl` trỏ đúng context.
- Cluster pull được image `busybox:1.36` và `nginx:1.27-alpine`.
- Command trong bài dùng Bash/WSL. Với PowerShell, cần đổi quoting cho `kubectl patch -p`.

## Lab Scenario

Bạn sẽ tạo nhiều Pod nhỏ để quan sát lifecycle của `emptyDir`, mount ConfigMap/Secret thành file, thử shared volume giữa init container và app container, rồi inject lỗi thiếu ConfigMap để đọc events.

## Core Path và Stretch Goals

- Core Path: Task 1-4, khoảng 100 phút.
- Stretch Goals: Task 5-6, dành cho `hostPath`, `projected` và `subPath` nếu còn thời gian.

## Task 1: `emptyDir` sống qua container restart nhưng không sống qua Pod deletion (25 phút)

### Mục tiêu

Hiểu đúng scope của `emptyDir`.

### Các bước thực hiện

```bash
kubectl create namespace day22
kubectl config set-context --current --namespace=day22
```

Tạo file `emptydir.yaml`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: emptydir-demo
spec:
  restartPolicy: Always
  volumes:
  - name: work
    emptyDir:
      sizeLimit: 128Mi
  containers:
  - name: app
    image: busybox:1.36
    command:
    - sh
    - -c
    - |
      if [ ! -f /work/restarted-once ]; then
        echo "first container start time=$(date -Iseconds)" >> /work/history.txt
        touch /work/restarted-once
        exit 1
      fi
      echo "after container restart time=$(date -Iseconds)" >> /work/history.txt
      sleep 3600
    volumeMounts:
    - name: work
      mountPath: /work
```

Apply và quan sát restart:

```bash
kubectl apply -f emptydir.yaml
kubectl wait --for=condition=Ready pod/emptydir-demo --timeout=90s
kubectl get pod emptydir-demo -w
```

Dừng watch bằng `Ctrl+C` sau khi thấy `RESTARTS` tăng lên. Sau đó kiểm tra:

```bash
kubectl exec emptydir-demo -- cat /work/history.txt
kubectl describe pod emptydir-demo
```

Xóa Pod và tạo lại:

```bash
kubectl delete pod emptydir-demo
kubectl apply -f emptydir.yaml
kubectl wait --for=condition=Ready pod/emptydir-demo --timeout=90s
kubectl exec emptydir-demo -- cat /work/history.txt
```

### Expected output

- File `/work/history.txt` vẫn còn sau container restart trong cùng Pod.
- Nội dung có cả dòng `first container start` và `after container restart`.
- Sau khi Pod bị xóa và tạo lại, history bắt đầu mới.

## Task 2: Shared volume giữa init container và app container (25 phút)

### Mục tiêu

Thấy `emptyDir` làm workspace chung trong Pod.

### Các bước thực hiện

Tạo file `init-shared.yaml`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: init-shared
spec:
  volumes:
  - name: site
    emptyDir: {}
  initContainers:
  - name: render-config
    image: busybox:1.36
    command:
    - sh
    - -c
    - |
      echo "generated by init container at $(date -Iseconds)" > /site/index.html
    volumeMounts:
    - name: site
      mountPath: /site
  containers:
  - name: nginx
    image: nginx:1.27-alpine
    ports:
    - containerPort: 80
    volumeMounts:
    - name: site
      mountPath: /usr/share/nginx/html
```

Apply:

```bash
kubectl apply -f init-shared.yaml
kubectl wait --for=condition=Ready pod/init-shared --timeout=90s
kubectl port-forward pod/init-shared 8080:80
```

Ở terminal khác:

```bash
curl http://localhost:8080
```

### Expected output

- NGINX serve file do init container tạo.
- App image không cần bake file đó sẵn.

## Task 3: Mount ConfigMap và Secret thành file (30 phút)

### Mục tiêu

Phân biệt config không nhạy cảm và secret khi mount vào filesystem.

### Các bước thực hiện

Tạo file `config-secret.yaml`:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  app.yaml: |
    logLevel: info
    featureFlag: "false"
---
apiVersion: v1
kind: Secret
metadata:
  name: app-secret
type: Opaque
stringData:
  password: "not-for-production"
---
apiVersion: v1
kind: Pod
metadata:
  name: config-secret-demo
spec:
  volumes:
  - name: config
    configMap:
      name: app-config
  - name: secret
    secret:
      secretName: app-secret
      defaultMode: 0400
  containers:
  - name: app
    image: busybox:1.36
    command:
    - sh
    - -c
    - |
      echo "config:"
      cat /etc/app/app.yaml
      echo "secret files:"
      ls -l /run/secret
      sleep 3600
    volumeMounts:
    - name: config
      mountPath: /etc/app
      readOnly: true
    - name: secret
      mountPath: /run/secret
      readOnly: true
```

Apply và inspect:

```bash
kubectl apply -f config-secret.yaml
kubectl wait --for=condition=Ready pod/config-secret-demo --timeout=90s
kubectl logs config-secret-demo
kubectl exec config-secret-demo -- ls -l /etc/app /run/secret
kubectl exec config-secret-demo -- cat /etc/app/app.yaml
```

### Expected output

- ConfigMap xuất hiện dưới `/etc/app/app.yaml`.
- Secret xuất hiện dưới `/run/secret/password` với mode hạn chế.
- Không in nội dung secret ra logs trong production.

## Task 4: Inject lỗi thiếu ConfigMap (20 phút)

### Mục tiêu

Đọc đúng lỗi volume từ events.

### Các bước thực hiện

Tạo file `broken-config.yaml`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: broken-config
spec:
  volumes:
  - name: missing
    configMap:
      name: does-not-exist
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 3600"]
    volumeMounts:
    - name: missing
      mountPath: /etc/missing
```

Apply và debug:

```bash
kubectl apply -f broken-config.yaml
kubectl get pod broken-config
kubectl describe pod broken-config
kubectl get events --sort-by=.lastTimestamp
```

Sửa bằng cách tạo ConfigMap:

```bash
kubectl create configmap does-not-exist --from-literal=app.yaml='fixed: true'
kubectl get pod broken-config -w
```

### Expected output

- Pod ban đầu không chạy được vì ConfigMap thiếu.
- `describe pod` chỉ rõ lỗi mount/setup volume.
- Sau khi tạo ConfigMap, Pod có thể chuyển sang Running.

## Task 5: Optional - quan sát `hostPath` trong lab (15 phút)

### Mục tiêu

Hiểu vì sao `hostPath` phụ thuộc node.

### Các bước thực hiện

Chỉ chạy trên lab cá nhân:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: hostpath-demo
spec:
  volumes:
  - name: node-tmp
    hostPath:
      path: /tmp
      type: Directory
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "echo pod=$HOSTNAME > /node-tmp/day22-hostpath.txt; sleep 3600"]
    volumeMounts:
    - name: node-tmp
      mountPath: /node-tmp
```

Apply nếu bạn hiểu rủi ro:

```bash
kubectl apply -f hostpath-demo.yaml
kubectl describe pod hostpath-demo
```

### Expected output

- Pod mount path từ node.
- Nếu Pod chạy ở node khác, data/path là node khác. Đây không phải storage portable.

## Task 6: Optional - `projected` và `subPath` update behavior (20 phút)

### Mục tiêu

Thấy `projected` gom nhiều nguồn vào một directory và `subPath` không nên dùng nếu kỳ vọng ConfigMap update tự động.

### Các bước thực hiện

Tạo file `projected-subpath.yaml`:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: projected-config
data:
  app.yaml: |
    version: v1
---
apiVersion: v1
kind: Secret
metadata:
  name: projected-secret
type: Opaque
stringData:
  token: demo-token
---
apiVersion: v1
kind: Pod
metadata:
  name: projected-demo
spec:
  volumes:
  - name: bundle
    projected:
      sources:
      - configMap:
          name: projected-config
      - secret:
          name: projected-secret
  - name: config-only
    configMap:
      name: projected-config
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 3600"]
    volumeMounts:
    - name: bundle
      mountPath: /bundle
      readOnly: true
    - name: config-only
      mountPath: /etc/app/app.yaml
      subPath: app.yaml
      readOnly: true
```

Apply và inspect:

```bash
kubectl apply -f projected-subpath.yaml
kubectl wait --for=condition=Ready pod/projected-demo --timeout=90s
kubectl exec projected-demo -- ls -l /bundle
kubectl exec projected-demo -- cat /bundle/app.yaml /etc/app/app.yaml
kubectl patch configmap projected-config --type merge -p '{"data":{"app.yaml":"version: v2\n"}}'
kubectl exec projected-demo -- cat /bundle/app.yaml /etc/app/app.yaml
```

### Expected output

- `/bundle` có cả file từ ConfigMap và Secret.
- File mount bằng `subPath` thường không phản ánh update ConfigMap như mount directory bình thường.

## Câu hỏi tự kiểm tra

1. `emptyDir` khác container writable layer ở đâu?
2. Vì sao `emptyDir` không phù hợp cho database?
3. `hostPath` phù hợp với workload nào và rủi ro gì?
4. ConfigMap mounted file khác ConfigMap env var thế nào khi update?
5. Vì sao `subPath` cần dùng thận trọng với ConfigMap/Secret?

## Đáp án ngắn

1. `emptyDir` thuộc Pod, chia sẻ được giữa containers và sống qua container restart.
2. Khi Pod bị xóa/reschedule, `emptyDir` mất nên không dùng cho database.
3. `hostPath` hợp cho node agent/DaemonSet; rủi ro security và node-local data.
4. Mounted file có thể refresh trễ; env var chỉ đổi khi Pod được recreate.
5. `subPath` thường không nhận update tự động từ ConfigMap/Secret mount.
