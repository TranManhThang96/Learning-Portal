## 1. Mục tiêu bài học

Sau bài học, bạn sẽ:

- Giải thích được Redis Streams internal: append-only log + radix tree (rax), tại sao entry ID `<ms>-<seq>` đảm bảo ordering.
- Implement được job queue hoàn chỉnh với XADD, XREADGROUP, XACK, PEL, và XAUTOCLAIM — biết khi nào mỗi command cần dùng.
- Phân tích trade-off giữa Streams vs Kafka vs RabbitMQ vs Pub/Sub, đưa ra recommendation dựa trên throughput, retention, durability, và operational complexity.
- Thiết kế được DLQ pattern để handle message retry exhaustion, tránh PEL phình to gây OOM.
- Monitor PEL size, tính memory cost của stream entries, và đặt XTRIM policy phù hợp cho từng use case.

## 2. Vì sao cần học chủ đề này

### Incident 1: LIST + LPOP Job Queue — Mất Job Khi Consumer Crash

Team dùng `LPUSH` producer và `BRPOP` consumer cho job queue.逻辑 đơn giản:

```
Producer: LPUSH queue:jobs <job-json>
Consumer: BRPOP queue:jobs 0  -> process -> next
```

Một consumer đang xử lý job, chưa xong, crash giữa chừng. Job đã `LPOP` ra khỏi queue — **mất vĩnh viễn**. Không có cách nào recover. Team phải implement "at-least-once" bằng tay: sau khi process xong mới `LREM`, nhưng nếu process xong rồi crash trước khi `LREM` → duplicate process. Hoặc dùng `BRPOPLPUSH` (safe queue pattern) nhưng chỉ hỗ trợ 1 consumer, không scale được.

**Streams + PEL fix hoàn toàn**: Consumer crash → message vẫn nằm trong PEL, consumer khác claim lại sau idle timeout.

### Incident 2: Stream Chiếm 20GB Vì Quên XTRIM

Một service ghi log vào Redis Stream. `XADD mystream * msg "..."`. Chạy 6 tháng, stream không bao giờ trim. 50 triệu entries × ~200 byte = **10GB raw data**, cộng radix tree overhead → 20GB. Redis `maxmemory` bị chạm → eviction policy `noeviction` → writes fail → toàn bộ service down.

Root cause: không ai đặt XTRIM policy, không ai monitor stream length.

### Incident 3: PEL 1M Entries — Consumer Lag Không Phát Hiện

Một consumer group có 3 consumers. Một consumer bug: process xong nhưng **không gọi XACK**. Message nằm trong PEL vĩnh viễn. Sau 3 ngày, PEL = 1M entries. `XINFO STREAM` trả về length = 1M nhưng không ai nhìn. Metric backlog bị tăng, nhưng team không có alert. Khi restart consumer, `XREADGROUP` đọc từ PEL → **1M entries cùng đổ vào consumer 1 lúc** → OOM, crash, cascading failure.

**Bottom line**: Streams giải quyết reliability problem mà LIST không có, nhưng nếu không hiểu PEL lifecycle, không monitor, không trim → tạo ra incident mới nghiêm trọng hơn.

## 4. Lý thuyết chi tiết

### 4.1. Redis Streams Internals — First Principles

Redis Stream là **append-only log** được tổ chức bên trong bằng **radix tree (rax)** — cùng data structure dùng cho sorted set nhưng tối ưu cho sequential access.

#### Tại sao radix tree?

```
Array/List-based approach (naive):
  Entry[0] Entry[1] Entry[2] ... Entry[N]
  - Insert O(1) at tail ✓
  - Read by index O(1) ✓
  - Read by range O(N) ✗
  - Memory: must keep all pointers

Radix Tree (rax) approach:
  - Insert O(k) where k = key length (ID length) ✓
  - Range query by prefix (ID range) O(k + M) ✓
  - Memory efficient for sparse data ✓
  - Sequential iteration via in-order traversal ✓
```

Redis dùng radix tree vì stream entries được query **theo ID range** (`XREAD ID > last-read`), không phải theo index. Radix tree lưu entry ID làm key → range scan cực nhanh.

#### Stream Internal Structure

```
Stream key "order:events":
  [Radix Tree]
    root
    ├── node (ms=1700000000000)
    │   ├── entry[1700000000000-0]: {user_id: "U001", amount: 50000}
    │   └── entry[1700000000000-1]: {user_id: "U002", amount: 120000}
    └── node (ms=1700000001000)
        ├── entry[1700000001000-0]: {user_id: "U003", amount: 75000}

  Consumer Groups metadata (stored separately):
    CG: "order-processors"
      last-delivered-id: "1700000000000-1"
      consumers:
        c1: PEL = [1700000000000-0]
        c2: PEL = []
```

Mỗi entry bên trong dùng **listpack** (không phải linked list) — compact, cache-friendly. Overhead ~150 byte/entry cho radix tree node + pointer.

### 4.2. Stream Entry ID Semantics

```
Format: <milliseconds>-<sequence-number>
Examples:
  "1700000000000-0"      ← auto-generated by XADD *
  "1700000000000-127"    ← auto-generated, seq=127
  "0-1"                  ← valid (ms=0, seq=1)
  "1700000000000-*?"     ← INVALID (no wildcard in ID)

ID generation rules:
  - XADD * : Redis lấy current server ms, tăng sequence number nếu cùng ms
  - Custom ID: "1700000000000-500" → dùng trực tiếp (useful cho data migration)
  - ID < last-generated: REJECTED với error "ID specified is smaller than last entry ID"

Ordering guarantee:
  - ID monotonic increasing → entries luôn sorted
  - 2 entries cùng ms: sequence number đảm bảo order
  - Consumer group delivery order = entry ID order (FIFO)

Anti-pattern: Custom ID không monotonic → break ordering, break XREADGROUP
```

### 4.3. Consumer Group State Machine

```
┌─────────────────────────────────────────────────────────────────────┐
│                     Consumer Group State Machine                      │
│                                                                      │
│  Stream Entry Created (XADD)                                         │
│         │                                                            │
│         ▼                                                            │
│  ┌──────────────┐    XREADGROUP    ┌─────────────────┐             │
│  │   STREAM     │ ────(>new)─────▶ │   Consumer's    │             │
│  │  (visible)   │                  │   Inbox (PEL)   │             │
│  └──────────────┘                  └────────┬────────┘             │
│         ▲                                    │                       │
│         │         XACK (success)              │ (process OK)        │
│         │────────────────────────────────────┘                       │
│         │                                                             │
│         │         XACK (fail)              ┌─────────────────┐      │
│         └───────────────────────────────▶  │  Re-claimable   │      │
│                                           │  after idle-time │      │
│                                           └────────┬────────┘       │
│                                                    │                 │
│                            XAUTOCLAIM / XCLAIM     │                 │
│                              (min-idle-time met)   ▼                 │
│                                           ┌─────────────────┐         │
│                                           │ New Consumer's │         │
│                                           │ Inbox (PEL)    │         │
│                                           └─────────────────┘         │
└─────────────────────────────────────────────────────────────────────┘
```

**PEL (Pending Entries List)** per consumer:

```
Consumer Group "payments" on stream "tx:stream":
  Last-acknowledged-ID: 1700000000000-99

  Consumer c1:
    PEL IDs: [1700000000100-0, 1700000000100-1, 1700000000100-2]
    → These 3 entries were delivered to c1, not yet XACK'd

  Consumer c2:
    PEL IDs: [1700000000103-0]
    → 1 entry delivered to c2, pending

  Consumer c3:
    PEL IDs: []
    → c3 has no pending entries
```

### 4.4. At-Least-Once vs Exactly-Once

```
At-least-once (Redis Streams default):
  Producer ──XADD──▶ Stream ──XREADGROUP──▶ Consumer
                     │                        │
                     │◀───── XACK ───────────┘
                     │
  "Message delivered at least once. May be duplicated."

Exactly-onast (application-level):
  1. XREADGROUP → get entry ID + payload
  2. Process payload
  3. Store processed-ID in Set: SADD processed:orders <entry-id>
  4. Check before process: SISMEMBER processed:orders <entry-id>
     - If exists → skip (already processed)
     - If not → process + XACK
  5. Periodic cleanup: ZREMRANGEBYSCORE processed:orders 0 <24h-ago>

Trade-off: exactly-once cần idempotency storage (~ Redis Set/HyperLogLog),
           tăng latency 1 RTT, tăng memory cho dedup index.
```

### 4.5. XAUTOCLAIM Behavior

```
XAUTOCLAIM stream group min-idle-time start [COUNT count] [JUSTID]

Step-by-step:
  1. Scan PEL entries where idle time > min-idle-time
  2. Claim those entries: remove from old consumer's PEL, add to new consumer's PEL
  3. Return claimed entry IDs + entry contents

  Example:
    XAUTOCLAIM tx:stream payments 30000 0-0 COUNT 10

    → Claim up to 10 entries idle > 30 seconds
    → Start scanning from PEL entry 0-0
    → Returns:
      1) next start ID for next call
      2) list of claimed entry IDs
      3) list of entry contents (payloads)

Common mistake: min-idle-time quá ngắn (ví dụ 100ms)
  → Race condition: consumer A đang process entry X, consumer B claim X
  → Result: 2 consumers xử lý cùng 1 entry (duplicate)

Recommendation:
  - min-idle-time = 2× average process time
  - Monitor claimed entries count → nếu > threshold → alert
```

### 4.6. Trimming — Approximate (~) vs Exact

```
XADD mystream MAXLEN ~10000 * field value
  → Approximate trim: Redis dùng macro-node heuristic
  → Không guarantee exact 10000 entries
  → Performance: O(1), không scan toàn bộ stream
  → Thực tế: thường trim về 10000±5%, accept được

XADD mystream MAXLEN 10000 * field value
  → Exact trim: Redis guarantee không quá 10000 entries
  → Performance: O(N) với N = entries vượt limit
  → Use case: hard limit bắt buộc (regulatory compliance)

XADD mystream MINID 1700000000000 * field value
  → Trim all entries with ID < specified ID
  → Useful for time-based retention
  → Example: XTRIM mystream MINID 1700000000000 (same logic)

Why ~N is better for most cases:
  - At 50K entries/sec, exact trim scans 50K entries on every XADD
  - Approximate trim uses listpack macro nodes (each ~100 entries)
  → Check 500 nodes instead of 50K entries → 100× faster
```

### 4.7. Memory Cost

```
Per-stream-entry memory:
  - Radix tree node overhead: ~32-48 bytes
  - Listpack entry: ~8-16 bytes (field) + ~8-16 bytes (value) + header
  - Consumer group PEL entry per consumer: ~40 bytes (entry ID + metadata)

Example calculation:
  1M entries in stream, 3 consumers, average payload 200 bytes:

  Raw data:              1M × 200B              =   200 MB
  Radix tree overhead:  1M × 40B               =    40 MB
  Listpack overhead:     1M × 16B               =    16 MB
  PEL (3 consumers avg): 1M × 3 × 40B           =   120 MB
  ─────────────────────────────────────────────────────────────
  Total:                                         =   376 MB

Rule of thumb: ~150 byte overhead per entry (không tính payload)
               + ~40 byte per PEL entry per consumer

XTRIM strategy:
  - Stream size budget: giới hạn MAXLEN sao cho memory predictable
  - Monitor XLEN output → alert khi > threshold
```

## 5. Trade-off Analysis

### Streams vs Kafka vs RabbitMQ vs SQS vs Pub/Sub

| Dimension | Redis Streams | Apache Kafka | RabbitMQ | AWS SQS | Redis Pub/Sub |
|---|---|---|---|---|---|
| **Delivery** | At-least-once | At-least-once / Exactly-once | At-least-once | At-least-once / Exactly-once | At-most-once (fire-and-forget) |
| **Persistence** | In-memory + AOF/RDB | Disk (segmented, OS page cache) | RAM + disk spillover | Managed, multi-AZ | None |
| **Retention** | Limited by memory | Days/weeks/months (disk) | Configurable | Infinite (cheap) | None |
| **Throughput** | ~50K-100K msg/s | ~1M+ msg/s | ~50K msg/s | ~300 msg/s per queue | ~100K msg/s |
| **Consumer group** | ✓ Native | ✓ Native (consumer group) | ✓ Via sharded queue | ✓ Via FIFO + deduplication | ✗ |
| **Replay** | ✓ By ID range | ✓ By offset | Partial | ✗ | ✗ |
| **Multi-DC** | ✗ Native (needs Redis Gossip/Sentinel/Cluster) | ✓ Native replication | ✗ (federation) | ✓ Managed cross-region | ✗ |
| **Ordering** | Per stream (ID order) | Per partition | Per queue | Per message group | None |
| **Operational** | Simple (Redis already in stack) | Complex (ZK/KRaft, brokers, topic config) | Medium | Zero (managed) | Simple |
| **Cost model** | Server cost | Infrastructure + ops | Server cost | Pay-per-use | Server cost |
| **Use when** | < 50K msg/s, retention < hours, Redis already in use | High throughput, long retention, multi-DC | General AMQP, complex routing | AWS shop, zero ops | Real-time fanout, no persistence needed |

### Streams vs Pub/Sub

| Scenario | Streams | Pub/Sub |
|---|---|---|
| Consumer offline for 1 hour | Message buffered in stream, delivered on reconnect | Message lost |
| 2 consumers need different processing | Can use separate consumer groups | Same message to all subscribers |
| Need to replay old messages | ✓ XREAD from specific ID | ✗ |
| Need acknowledgment | ✓ XACK/PEL | ✗ |
| Fire-and-forget, no persistence needed | Overkill | ✓ Perfect fit |
| At-least-once reliability | ✓ Native | ✗ |

### Consumer Group vs Simple Consumer

| Aspect | Consumer Group (XREADGROUP) | Simple Consumer (XREAD) |
|---|---|---|
| Load balancing | ✓ Multiple consumers, parallel processing | ✗ Single consumer (or manual partition) |
| Crash recovery | ✓ PEL preserves unACK'd messages | ✗ Message lost if consumer crashes |
| Complexity | Higher | Lower |
| Use when | Multiple workers, reliability critical | Single consumer, fire-and-forget acceptable |
| Idempotency | Must handle (PEL ≠ guaranteed exactly-once) | Same issue |

### Trimming by Length vs by Time

| Approach | Command | Best for | Risk |
|---|---|---|---|
| By length | `XADD s MAXLEN ~100000 * ...` | Throughput-focused, unbounded growth | Approximate (may exceed by ~5%) |
| By length (exact) | `XADD s MAXLEN 100000 * ...` | Hard limit (regulatory) | Slower at scale |
| By time (ID) | `XTRIM s MINID <24h-ago-id>` | Time-based retention | ID calculation complexity |
| Kết hợp length + time | `XADD ... MAXLEN ~N` ở write path + job định kỳ `XTRIM s MINID <id>` | Vừa có safety cap vừa có retention theo thời gian | Cần tính `MINID` và monitor cả `XLEN` lẫn memory |

## 6. Best Solution & Best Practices

### Khi nào dùng Redis Streams

- **Throughput < 50K-100K msg/s sustained**: Streams chạy trên Redis single-threaded, overhead quản lý consumer group + PEL tăng theo msg/s
- **Retention < vài giờ**: Streams lưu trong memory; retention dài → memory cost cao
- **Redis đã có trong stack**: Không cần deploy thêm infrastructure
- **Event log volume vừa**: Audit log, notification queue, order processing, job queue
- **Cần replay**: Debug, reprocess, backfill
- **On-prem hoặc private cloud**: Không có managed Kafka/Pub/Sub

### Khi nào dùng Kafka

- **Throughput > 100K msg/s sustained**: Kafka xử lý bằng disk sequential read, không bị single-threaded constraint
- **Retention ngày/tuần/tháng**: Kafka dùng disk, retention dài không tốn memory
- **Multi-datacenter replication**: Kafka MirrorMaker/Replicator hỗ trợ tốt
- **Schema evolution**: Kafka schema registry, Avro/Protobuf
- **Event sourcing dài hạn**: Audit trail, compliance
- **Stream processing**: Kafka Streams, Apache Flink integration

### Anti-patterns cần tránh

1. **Không trim stream**: Dùng `XADD *` không `MAXLEN` → stream phình không kiểm soát → OOM
2. **Không monitor PEL**: Không có alert khi PEL > threshold → lag âm thầm
3. **Consumer không idempotent**: Process 2 lần cùng 1 message → duplicate data/action
4. **Dùng Streams thay event sourcing dài hạn**: Streams là in-memory append-only log, không phải database; dùng cho event sourcing dài hạn → memory exhaustion
5. **XAUTOCLAIM min-idle-time quá ngắn**: Gây race claim → duplicate process
6. **Không handle BUSYGROUP**: `XGROUP CREATE` fail nếu group đã tồn tại → cần `MKSTREAM` hoặc try/catch
7. **Không có DLQ**: Message fail forever → PEL tăng mãi mãi
8. **Consumer group trên replica**: Consumer groups chỉ hoạt động trên primary node (Redis 7.2 và trước); đọc từ replica có thể miss entries

### Best Practices Checklist

- [ ] Always specify `MAXLEN ~N` với XADD để bound memory
- [ ] Monitor `XPENDING stream group` — alert khi count > threshold (vd: > 10K)
- [ ] Implement DLQ: sau N retry → `XADD stream:dlq <entry>` + `XACK`
- [ ] Consumer phải idempotent: dùng Set/HyperLogLog check trước khi process
- [ ] `XGROUP CREATE` với `MKSTREAM` để tự động tạo stream khi chưa có
- [ ] Đặt `min-idle-time` trong XAUTOCLAIM = 2× p99 process time
- [ ] Dùng `COUNT` với XREADGROUP để batch process, tránh một lần chỉ lấy 1 message
- [ ] Stream name gồm namespace: `app:entity:events` (vd: `orders:created`)

## 7. Performance Considerations

### Command Latency

```
Command         | Complexity      | Latency (p99)   | Notes
----------------|-----------------|-----------------|--------------------------
XADD            | O(log N)        | ~1-3 µs         | N = stream length
XLEN            | O(1)            | ~0.5 µs         | Cached counter
XREAD           | O(log N + M)    | ~5-20 µs        | M = count
XREADGROUP      | O(log N + M)    | ~10-30 µs       | + CG lookup overhead
XACK            | O(M)            | ~2-5 µs         | M = PEL entries per consumer
XPENDING        | O(M)            | ~5-15 µs        | M = pending count
XAUTOCLAIM      | O(M)            | ~20-50 µs       | M = claimed entries
XTRIM           | O(1) amortized  | ~10-30 µs       | ~N macro-node check
```

### XREADGROUP BLOCK — Blocking vs Polling

```
Non-blocking (XREADGROUP COUNT 10 mystream cg1 c1):
  - Returns immediately, empty array if no new messages
  - Consumer loop must sleep manually → CPU spin or sleep overhead

Blocking (XREADGROUP BLOCK 5000 COUNT 10 mystream cg1 c1):
  - Blocks up to 5000ms waiting for new messages
  - Efficient: Redis pushes when data arrives (via client buffer)
  - Recommended for most consumer patterns
  - BLOCK 0 = infinite (use with timeout in application)

BLOCK tuning:
  - BLOCK 100ms: Low latency, higher Redis CPU (more empty polls)
  - BLOCK 5000ms: Better throughput per poll, higher message latency
  - Recommendation: BLOCK 1000-5000ms for balanced workloads
```

### PEL Size Thresholds

```
PEL < 1K entries / consumer: Normal operation
PEL 1K-10K entries / consumer: Monitor, investigate
PEL > 10K entries / consumer: ALERT — consumer lag or bug (no XACK)
PEL > 100K entries / consumer: CRITICAL — likely XACK missing, immediate action

PEL growth rate = delivery rate - XACK rate
  → Alert when PEL grows > X entries/minute sustained
```

### Memory Budget Planning

```
Scenario: 10K orders/minute, average payload 500 bytes, retention 2 giờ

Entries:      10,000/min × 120 min   = 1,200,000 entries
Raw data:     1.2M × 500B             =   600 MB
Stream overhead: 1.2M × 150B          =   180 MB
PEL (3 consumers): 1.2M × 3 × 40B    =   144 MB
──────────────────────────────────────────────────────────────
Total:                                 =   924 MB ≈ 1 GB

If MAXLEN ~50000 per consumer group:
  Raw:       50K × 500B                =    25 MB
  Overhead:  50K × 150B                =     8 MB
  PEL:       50K × 3 × 40B            =     6 MB
  ───────────────────────────────────────────────────────────
  Total:                                 =   39 MB (per consumer group)
```

## 8. Production Failure Modes

### 8.1. Consumer Crash → PEL Phình To

```
Symptom: XPENDING shows growing count, XINFO GROUPS shows high "pending"
Cause: Consumer process xong nhưng không gọi XACK trước khi crash
Detection:
  - Alert on: XPENDING count > 10K sustained > 5 min
  - Monitor: consumer group lag metric
Fix:
  - XAUTOCLAIM with appropriate min-idle-time
  - Find buggy consumer: XINFO GROUPS → look for consumer with high pending
  - Add XACK only after process thành công hoặc sau khi đã move sang DLQ
Prevention:
  - Wrap processing in try/catch/finally, nhưng không ACK transient failure
  - Idempotent processing đảm bảo retry/claim không gây side effect trùng
```

### 8.2. Stream Không Trim → OOM

```
Symptom: Redis OOM, maxmemory reached, writes rejected
Cause: XADD without MAXLEN, retention unbounded
Detection:
  - Alert on: XLEN > configured threshold
  - Monitor: Redis used_memory > 80% maxmemory
Fix:
  - XTRIM mystream MAXLEN ~<safe-limit>
  - Immediate: XTRIM to reduce size
  - Long-term: Set MAXLEN in XADD command
Prevention:
  - Default to XADD with MAXLEN ~100000 (tune per stream)
  - Alert on stream length growth rate > threshold
```

### 8.3. XAUTOCLAIM Race Condition

```
Symptom: Same message processed by 2 consumers
Cause: min-idle-time too short — consumer A still processing, B already claims
Timeline:
  T=0:   Consumer A reads message M, starts processing
  T=100ms: Consumer A still processing (process takes 5s)
  T=101ms: Consumer B runs XAUTOCLAIM min-idle-time=100ms → claims M
  T=5s:   Consumer A finishes, XACK(M) → "ID not in PEL" (already moved)
  T=5.1s: Consumer B processes M again

Fix: Set min-idle-time = 2× p99 process time
     Recommended: 60000ms (1 min) minimum for most workloads
```

### 8.4. Consumer Not Idempotent → Duplicate Processing

```
Symptom: Order processed twice, notification sent twice, etc.
Cause: Message delivered, consumer hoàn tất side effect nhưng crash trước XACK;
       message còn trong PEL và sẽ bị XAUTOCLAIM bởi consumer khác
Fix:
  - Check idempotency key BEFORE processing:
    SISMEMBER processed <entry-id> → if yes, skip + XACK immediately
  - Store idempotency key trong cùng transactional boundary với side effect nếu có thể
  - Nếu side effect ngoài Redis, dùng idempotency key ở downstream service
```

### 8.5. Consumer Group Gửi Nhầm Tới Replica

```
Symptom: Consumer loop gặp READONLY/error hoặc không update được PEL/delivery state
Cause: XREADGROUP/XACK/XAUTOCLAIM thay đổi consumer-group metadata nên phải đi tới primary
Fix: Route toàn bộ consumer-group command tới primary; chỉ dùng replica cho read-only XREAD/XRANGE nếu chấp nhận stale data
Note: Replica read phù hợp cho analytics read-only, không phù hợp cho worker queue có ACK/claim
```

## 9. Real-world Examples

### DoorDash: Order Event Pipeline

DoorDash dùng Redis Streams cho **order lifecycle events** trong microservices architecture. Mỗi trạng thái đơn hàng (created, confirmed, preparing, picked_up, delivered) được XADD vào stream `order:events`. Consumer group `order-state-machine` có consumers cho từng service (notification, analytics, driver-matching).

Lý do chọn Streams thay Kafka: DoorDash bắt đầu từ Redis cho caching/session, thêm Streams không cần deploy thêm Kafka cluster. Order volume < 50K/min, retention chỉ cần vài giờ (đủ cho reprocess nếu incident).

Kết quả: Latency từ XADD đến consumer nhận < 10ms p99. Consumer groups đảm bảo at-least-once cho billing events.

### GitLab: Background Job Processing

GitLab từng dùng Sidekiq (Redis-backed job queue) với LIST-based storage. Chuyển một phần workload sang Streams để:
- **Replay support**: Khi deploy gây bug, có thể replay events từ stream thay vì yêu cầu user resubmit
- **Consumer group cho job priority**: High-priority jobs dùng group `priority-workers`, normal jobs dùng `default-workers`

Code pattern:
```
XADD jobs:stream MAXLEN ~50000 * job_type "email_notification" payload <data>
XREADGROUP GROUP priority-workers consumer1 BLOCK 1000 COUNT 5 STREAMS jobs:stream ">"
```

### RedisLabs Case Study: IoT Sensor Ingestion

## 10. Common Pitfalls

| Pitfall | Symptom | Fix |
|---|---|---|
| `XADD *` without `MAXLEN` | Stream grows forever → OOM | Always use `XADD s MAXLEN ~N` |
| Not calling `XACK` after successful process | PEL grows indefinitely | ACK success hoặc ACK sau khi move sang DLQ; không ACK transient failure |
| Dùng `>` để recover pending | Bỏ qua PEL nên tưởng mất message | Dùng `XPENDING` + `XAUTOCLAIM` hoặc đọc pending của chính consumer bằng ID cụ thể |
| Not handling `BUSYGROUP` error | App crash on restart if group exists | Use `MKSTREAM` or check before create |
| No DLQ | Failed messages stay in PEL forever | `XADD dlq:* * ...` on retry exhaustion |
| `min-idle-time` too short in XAUTOCLAIM | Race claim → duplicate processing | Set = 2× p99 process time |
| Single consumer in group | No parallelism | At least 2-3 consumers per group |
| Not monitoring PEL | Silent lag buildup | Alert on XPENDING > threshold |
| Confusing `XTRIM` vs `MAXLEN` | Trimming after the fact vs at write time | Use MAXLEN in XADD for real-time trim |
| Consumer group command routed to replica | READONLY/error hoặc không update PEL | Route XREADGROUP/XACK/XAUTOCLAIM tới primary |

## 11. Câu hỏi tự kiểm tra

### Câu 1: Consumer Group Re-balance

Bạn có 1 consumer group `payments` với 3 consumers. Consumer C1 crash. Sau 60 giây, bạn chạy:

```txt
XAUTOCLAIM payments-stream payments 30000 0-0 COUNT 100
```

Sau đó C2 và C3 đọc message. Message nào được claim? Tại sao `min-idle-time` phải lớn hơn thời gian xử lý trung bình?

> **Đáp án**: Messages trong C1's PEL idle > 30 giây được claim. Nếu xử lý trung bình 10 giây, 30 giây là đủ. Nhưng nếu có message cần 45 giây để xử lý, C1 đang xử lý khi claim xảy ra → **race condition**: C2/C3 process trùng message. min-idle-time phải > 2× p99 process time.

### Câu 2: Memory Incident

Một service ghi 10K messages/giây, mỗi message 200 bytes, không có XTRIM. Sau 1 ngày, stream có bao nhiêu entries? Memory ước tính bao nhiêu? Nếu maxmemory = 8GB, khi nào sẽ OOM?

> **Đáp án**:
> - 10K/sec × 86400sec = 864 triệu entries
> - Memory: 864M × (150B overhead + 200B payload) ≈ 300 GB → OOM ngay lập tức
> - Với MAXLEN ~1M: stream bounded ở ~1M × 350B ≈ 350 MB (hoàn toàn safe)
> - Lesson: không có XTRIM → incident guaranteed

### Câu 3: Kafka vs Streams Decision

Hệ thống IoT: 50K sensors, mỗi sensor gửi 1 reading/5 giây = 10K readings/giây. Cần retention 7 ngày cho compliance. Đọc real-time dashboard + replay incidents. Chọn Redis Streams hay Kafka? Giải thích.

> **Đáp án**:
> - Retention 7 ngày × 10K/sec × 200 bytes ≈ **120 GB raw data**
> - Redis Streams: memory-resident → 120 GB RAM cần thiết → **quá đắt**
> - Kafka: disk-based, 120 GB disk rất cheap → **Kafka là lựa chọn đúng**
> - Redis Streams phù hợp nếu: retention < vài giờ, throughput < 50K/sec, Redis đã có trong stack

### Câu 4: At-Least-Once Implementation

Viết pseudo-code cho consumer idempotent với XREADGROUP:

```go
for {
    entries := XREADGROUP("g1", "c1", "s", ">", "COUNT", 10)
    for entry := range entries {
        id := entry.ID
        if SISMEMBER("processed", id) == 1 {
            XACK("s", "g1", id)  // already done, just ACK
            continue
        }
        result := process(entry.Data)
        if result.Success {
            SADD("processed", id)
            XACK("s", "g1", id)
        } else {
            // don't ACK → stays in PEL → will be redelivered
            incrementRetryCount(id)
        }
    }
}
```

Sau bao nhiêu lần retry thì nên đẩy vào DLQ? Làm thế nào?

> **Đáp án**: Sau 3-5 retry (tùy business critical). Check retry count từ Set hoặc Hash:
> ```go
> retry := HINCRBY("retry-count", id, 1)
> if retry >= 5 {
>     XADD("orders:dlq", "*,
>         "original-id", id,
>         "payload", entry.Data,
>         "reason", "max-retries-exceeded")
>     XACK("orders:stream", "order-processors", id)
> }
> ```

### Câu 5: PEL vs Dead Letter

Giải thích sự khác nhau giữa PEL và DLQ. Khi nào message nằm trong PEL mãi mãi mà không bao giờ được xử lý?

> **Đáp án**:
> - **PEL**: Message đã delivered đến consumer nhưng chưa XACK. Vẫn đang "in-flight", sẽ được redelivered sau crash/idle.
> - **DLQ**: Message đã thử xử lý N lần thất bại, không còn muốn retry. Lưu trữ để human review.
>
> Message nằm trong PEL mãi mãi khi:
> 1. Consumer không XACK (bug hoặc crash trước khi XACK)
> 2. Không có XAUTOCLAIM cron job chạy định kỳ
> 3. Consumer crash vĩnh viễn, không ai claim lại
> → Solution: monitor PEL size, run XAUTOCLAIM periodically, implement DLQ

### Câu 6: XREADGROUP `>` vs `0-0`

Giải thích sự khác biệt giữa đọc với `>` và đọc với specific ID như `0-0`. Khi nào dùng cách nào?

> **Đáp án**:
> - `>`: Với `XREADGROUP`, đọc **message mới chưa từng delivered cho group**. Bỏ qua PEL. Dùng trong normal processing loop.
> - `0-0` hoặc ID cụ thể: Với `XREADGROUP`, đọc **pending entries của chính consumer hiện tại**, không phải toàn bộ stream. Dùng để recover sau restart cùng consumer name.
> - Backfill từ đầu: tạo consumer group với `XGROUP CREATE stream group 0` rồi đọc bằng `>`; hoặc dùng `XREAD`/`XRANGE` nếu không cần consumer-group state.
> - Pending của consumer khác: dùng `XPENDING` để quan sát và `XAUTOCLAIM`/`XCLAIM` để chuyển ownership.

### Câu 7: Trimming Strategy

Bạn có stream `audit:events`. Yêu cầu:
- Real-time processing: messages được xử lý trong 1 giờ
- Compliance: không cần giữ quá 7 ngày
- Throughput: ~5K events/giày

Đề xuất trimming strategy với Redis 7.2+?

> **Đáp án**:
> - Daily trim: `XTRIM audit:events MINID <7-days-ago-id>` (nightly cron)
> - At write time: `XADD audit:events MAXLEN ~100000 * ...` (hard cap)
> - Memory budget: 5K/day × 7 days × 500B payload ≈ 17.5 MB raw + overhead → **rất nhỏ**
> - Recommendation: Kết hợp both — MAXLEN ~100K for safety, nightly MINID trim for compliance
> - Không cần approximate vs exact trade-off ở volume này (5K/day = 35K entries/week << 100K cap)
